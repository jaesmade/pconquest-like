# Extending the early build

This guide describes the code that exists now and the contracts to keep stable as the game grows. The current run has a ten-column route with repeated encounter templates and simple enemy decisions.

Project development guidance lives in `AGENTS.md` and `docs/`. The former project-local `awesome-gamedev-agent-skills` bundle and its lock file were removed; extending the game does not depend on that skill pack.

The [scalability review](SCALABILITY_AUDIT.md) records the current growth limits and priorities for larger battles and content packs.

The [32×32 competitive 8v8 reassessment](SCALABILITY_TARGETS.md) sets the map ceiling alongside 20 total owned Pokémon per player and a 60 FPS rendering target. The current solo build supports up to 20 owned Pokémon and deploys six; competitive 8v8 and release performance remain future milestones.

## Where changes belong

| Area | Current home | Additions |
| --- | --- | --- |
| Types and multipliers | `src/content/typeChart.ts` | Keep the imported 18-type chart and dual-type multiplication here. |
| Abilities | `src/content/abilities.ts` | Add a stable ability name, description, and supported effect settings. Species and Mega forms reference these names. |
| Move definitions | `src/content/moves.ts` | Add a stable move key, type, category, power, range, target mode, AP cost, move tags, optional `visualId` and `soundId`, area and effects, and description. Use the [animation](ANIMATION_ASSETS.md) and [audio](AUDIO_ASSETS.md) guides for assignable placeholder IDs. |
| Species, stats, learnsets, evolution | `src/content/species.ts` | Add species keyed by stable ID; distinguish level learnsets from `tmMoves` compatibility. Put new starter and recruit IDs in their lists. |
| Party draft and run roster | `src/content/roster.ts` | Set the point budget, default or species-specific draft cost, and 20-Pokémon owned cap. |
| Route and shop | `src/game/route.ts`, `src/content/shop.ts` | Keep seeded node IDs, ten-column reachability, node rewards, item prices, and save migration aligned. See [route behavior](ROUTE_OVERHAUL.md). |
| Held items and TMs | `src/content/items.ts` | Add a stable item name and description. Held items use passive or Special effect settings; TMs use `teachesMove` and cannot be held. |
| Terrain and deployment zones | `src/content/maps.ts` | Use `createMap` with rectangular terrain, elevation, and A/N/E zone rows, plus default spawn coordinates. |
| Run order and rewards | `src/content/encounters.ts` | Add an encounter ID, `nextId`, map ID, enemy species IDs, enemy level, objective, and XP reward. |
| Cross-reference checks | `src/content/catalog.ts` | Extend `validateCatalog` when a new content relationship is introduced. |
| Battle state and rules | `src/game/types.ts`, `src/game/engine.ts`, `src/game/moveEffects.ts` | Keep battle scheduling in the engine and put each move-effect family's validation, resolution, preview, and AI score in its handler. |
| App bootstrap and run flow | `src/main.tsx`, `src/app/App.tsx` | Keep catalog validation and save loading in the bootstrap. Run state, save scheduling, and battle commands belong in the app controller. |
| Menus and battle display | `src/ui/`, `src/battle/Board.tsx` | Each route, title, preparation, stop, intermission, result, or battle screen owns its markup. Keep React controls separate from Phaser grid rendering. The battle screen loads on demand. |
| Screen styling | `src/styles/` | `base.css` loads first, then battle, menus, route, battle action rules, `theme.css`, and `battle-menu.css`. Keep that order when moving overrides; use the shared palette tokens for new UI. |
| Run persistence | `src/persistence/save.ts` | Bump the schema version and migrate older saves when the saved state shape changes. |
| Visual assets | `public/assets/animations/` | Follow the [unit, move, and ability authoring guide](UNIT_MOVE_ABILITY_ASSETS.md) for names and registration, then the [animation asset guide](ANIMATION_ASSETS.md) for frame details. |
| Audio assets | `public/assets/audio/`, `src/audio/audio.ts` | Follow [the audio asset guide](AUDIO_ASSETS.md); add named move, item, and music URLs to the manifest without changing battle rules. |

`src/content/data.ts` is a barrel for existing imports. New content can live in its focused file; battle scheduling stays in `src/game/engine.ts`, while effect-family rules live in `src/game/moveEffects.ts`.

`src/main.tsx` is only the entry point: it imports styles, validates content, loads the save, and mounts `App`. `src/app/App.tsx` coordinates the run and passes callbacks to screens in `src/ui/`. Shop and special choices render through `RouteStopScreen`; XP and level-up move choices through `IntermissionScreen`; held items, TM use, and ordinary evolution through `RouteScreen`; completion through `ResultScreen`. These screens do not own or serialize battle state. The split CSS files preserve the previous stylesheet order; `theme.css` applies the shared palette and `battle-menu.css` styles the glass action menu last. See the [UI overhaul plan](UI_OVERHAUL_PLAN.md) for color and typography conventions.

## Adding a Pokémon or move

1. Give the species and moves stable IDs. Existing IDs are stored in browser saves, so rename them only with a migration.
2. Add moves in `moves.ts` and the species' seven stats, types, ability, four distinct starting moves, level learnset, and optional `tmMoves` compatibility in `species.ts`. Stats are HP, Attack, Defense, Special Attack, Special Defense, Speed, and Movement, in that order. Four moves are equipped at once; a newly eligible level move can replace a slot only on the XP screen, and a TM can do so from the route Bag. Add `mobility: { fly: true }` or `{ swim: true }` for a form that needs it beyond the Flying/Water type defaults. Register any new ability in `abilities.ts` before assigning it to a species.
   The first six values are base combat stats. `statsAtLevel` floors `2 × base × level / 100`, then adds `level + 10` for HP or `5` for Attack, Defense, Special Attack, Special Defense, and Speed. Movement is a fixed tile range copied directly from the species record.
3. Add the species ID to `STARTERS`, `RECRUITS`, or an encounter only when it should appear there. A defined species can exist without joining either list.
4. Add battle art or let the renderer use the shared placeholder. New moves use role-based visual and sound placeholders automatically; set `visualId` and `soundId` to choose others. Add a named manifest entry keyed by the move ID when unique art or sound is ready.
5. Set an AP cost, tags, and an existing target area and effect in the move definition. `tags` is an array, so a move can have several. Supported tags are `contact`, `punch`, `bomb`, `projectile`, `pulse`, `sound`, `weather`, and `hazard`. Tag by what the move actually does: a future punching move would usually use `['punch', 'contact']`, while a thrown bomb could use `['bomb', 'projectile']`. The current starter moves have no punch or bomb move, so those tags are ready for future content without mislabeling Rock Throw or Tackle. Ability damage bonuses can use `requiredTag`; Tough Claws and Static now read the `contact` tag. The effect handlers cover status, displacement, tile effects, chain damage, stat stages, and weather. One move use, including a Status move, consumes that Pokémon's Attack command for the turn; movement and Special can still spend remaining AP. Existing item hooks cover round healing and threshold healing, Special Defense, Status move restrictions, Attack boosts, and Mega Evolution.

### Extending a move effect

Add a variant to `MoveEffect` in `src/game/types.ts`, then add its handler in `src/game/moveEffects.ts`. Each handler supplies `validate`, `resolve`, `preview`, and `score`. Startup catalog validation calls `validate`; combat calls `resolve`; the move hover card calls `preview`; and the solo enemy planner calls `score` to judge Status moves and break ties between damaging moves. The score hook reads battle state only and must not consume seeded RNG. The resolver may draw RNG through the battle's `random` function; any animation tiles it adds go on the provided visual cue and do not determine combat outcomes.

Execution order is fixed: cast effects run in their definition order, then direct targets are hit in battle-unit order; after each successful direct hit, its hit effects run in definition order. A chained hit checks that second defender's own accuracy, immunity, ability, and damage calculation, but does not repeat contact reactions or hit effects. Keep that distinction when adding a new effect. `src/game/engine.ts` owns AP spending, direct damage, and this phase order; no generic event bus is involved.

To add a held item, give it a stable name in `items.ts` and choose an existing effect shape. Consumables set `consume: true`; the battle unit keeps an Attack multiplier after X Attack is consumed. A Mega form is a complete species entry with its own stable ID, types, ability, stats, movement, moves, and art key. Put `form: { kind: 'mega', from: '<base-species-id>', stone: '<item-id>' }` on that form entry; do not nest Mega stats under the base species. `megaFormFor` indexes those relations for stone compatibility and battle transformation. Keep temporary forms out of starter and recruit lists. Item names and form species IDs are saved, so renaming either needs a migration.

Startup validation reports missing types, moves, evolutions, Mega Stones, encounter species, maps, objectives, spawn capacity, unusable deep-water spawns, and encounter-link cycles. It does not validate gameplay balance.

## Adding a map or encounter

`createMap` accepts terrain rows (`.` plain, `~` deep water, `^` lava, `#` wall), matching elevation rows (`0`–`2`), and matching zone rows (`A` ally, `N` neutral, `E` enemy). All rows must have the same width, with a maximum of 32 rows and 32 columns. Every tile belongs to exactly one zone, and each side needs at least eight plain deployment tiles for future 8v8 battles. Default player spawns must be plain ground in the ally zone; enemy spawns must be in the enemy zone and off lava. Spawns must be unique. Every plain, unobstructed ally or enemy deployment tile and the capture tile must be reachable from the first ally spawn by a grounded Pokémon using the battle movement rules: deep water is impassable, elevation changes require correctly facing slopes, and walls and solid objects block movement. A neutral tile may be isolated if it is not a capture objective. Coordinates are zero based `[x, y]`.

During preparation, select a Pokémon and click a legal ally-zone cell; clicking an occupied cell swaps the two placements when both can use the destination. Water requires swimming or flight, and lava and walls are unavailable for deployment. The solo opponent chooses distinct legal enemy-zone cells using the battle's seeded RNG. `startBattle(run, enemyDeployment)` also accepts an explicit ordered enemy placement and rejects invalid, missing, or duplicate cells for a future competitive opponent. Neutral tiles cannot be used during deployment. Once battle starts, the zones do not restrict movement. Selected placements are part of the run save; older saves receive legal default positions.

Add the map to `MAPS`, then reference its ID from an entry in `ENCOUNTERS`. The encounter determines enemy species, objective (`defeat` or `defeat-and-capture`), and XP. An encounter using the capture objective needs a map capture tile. The engine and Phaser board use the map's actual width and height for movement, attack areas, rendering, and weather cues. Existing example maps use 8×8 layouts; they are examples rather than a board-size requirement.

Encounter validation also checks each player species available through the starter/recruit evolution lines and each enemy species against every deployment cell it can legally use. Swimmers and flyers must be able to leave their chosen zone and reach the opposing land zone under their own mobility rules. An enemy water deployment must have adjacent ground that a grounded opponent can reach, so a water occupant can be confronted from shore. These are connectivity checks; they do not promise that a route through lava is survivable or that an AI will choose a good path.

The ten-column route records visited node IDs and the current node in the run. `run.encounter` tracks the current column for the UI. Authored encounters remain templates for map, enemy team, and objective; route battle and elite nodes adjust level, roster size, XP, and coins. The boss always uses the final authored map in column ten. Adding a node kind needs both a route resolver and saved-state migration.

## Saves and future rule families

The current format is v19 in the browser's IndexedDB database `pokemon-tactics-saves`. The `current` slot holds `{ schemaVersion, savedAt, run }` as JSON; the `backup` slot holds the previous complete snapshot. The run saves its route plan, visited nodes, coins, selected deployment coordinates, current node, and pending level-up move choices. Battle maps save an authored map ID and signature plus changed tiles; the signature includes deployment zones. Units retain combat state, seeded RNG, owned hazard zones, and per-stat stage expiry, while transient animation events are omitted. Tile `hazardUntil` is derived from zones and omitted from v13 and later map changes. Loading restores the authored map, applies changed tiles, validates the battle, rebuilds hazard tiles, and falls back to the backup if the current slot is malformed. A changed authored map restarts that battle at preparation with a report message.

v7–v18 saves are accepted and subsequent writes use v19. Pre-v16 runs receive a generated ten-column route with center-lane history matching completed encounters; v16–v17 runs remap their visited route progress and current node onto the expanded two-to-four-node graph. Current battles remain attached to their existing encounter template. The loader keeps party level and XP; v7–v10 saves also rescale current HP by the old and new maximum HP and return active battles to preparation because those units used the older combat-stat formula. A v11 battle resumes after its unit Movement values are restored from species data. Existing active Stealth Rock tiles in pre-v13 battles become temporary legacy zones with their original expiry because those saves did not record the caster; new casts cannot retroactively replace an unidentified old zone. Stages in pre-v14 active battles are capped at ±3 and receive a fresh 200 battle-time expiry, since their original application time was not saved. Loading accepts v7–v19 IndexedDB saves, v6 through v2 localStorage saves, and the older `pokemon-tactics-prototype-v1` shape. Pre-v17 saves keep their existing equipped moves, then gain missing species starting moves and fill the new four-slot loadout; active battle units receive four moves without changing seeded combat state. v18 and earlier runs migrate with an empty pending move queue, retain their current equipped slots, and do not replay prior level-up offers. Legacy localStorage keys remain a fallback. React batches normal writes for 700 ms during battle and 150 ms outside battle, and requests a final write when the page is hidden or closed; an abrupt browser termination can still lose the latest unsaved command. Storage failure appears in the top bar.

## Damage calculation

`src/game/damage.ts` is the single source for combat damage and UI ranges. It uses the attacking Pokémon's level, move power, the relevant Attack/Defense pair, standard stat stage ratios capped at −3 to +3, and integer base damage. Weather, a 1.5× critical hit, one of 16 equally likely random rolls from 85% to 100%, 1.5× same-type attack bonus, type effectiveness, and physical burn are applied in that order. Critical hits ignore negative offensive stages and positive defensive stages. The UI reports the possible normal and critical damage ranges; it does not consume battle RNG. The engine rolls critical chance (1 in 24) and damage variation when each target is hit.

Ability power bonuses are applied to base power, item Attack and Special Defense bonuses to the relevant stat, and snow/sandstorm defensive bonuses to Defense/Special Defense. Grid range, AP costs, terrain hazards, and secondary effects remain independent of direct move damage. New move-specific damage rules should be added as explicit calculator hooks rather than folded into a single final multiplier. Species stat growth in this fangame is still custom, so matching this damage pipeline does not imply complete main-series battle simulation.

When changing persisted fields, raise the schema version, keep a migration for existing versions, and preserve content IDs or map them explicitly. If a removed species, move, or encounter can occur in an old run, migrate it to an available replacement or reset that run deliberately; a type assertion alone cannot make old data valid.

Ability and item definitions and their supported effect settings live in `abilities.ts` and `items.ts`. Move definitions and areas live in `moves.ts`, with effect-family handlers in `moveEffects.ts`; pathfinding and line of sight live in `grid.ts`. Mobility capability and current state live in `mobility.ts` and on each battle unit. The Phaser board reads that state to draw a flight shadow or swim ripple. Keep the AP scheduler independent of effect handlers so Speed controls AP gained each round.

The deployment SVG now keeps authored-map cell geometry and terrain elements stable across placement edits, indexes occupants by cell, and omits empty actor groups. It still renders a hit polygon for each tile; profile a future 32×32 preparation screen before introducing culling. The board creates a Phaser sprite and HP bar for each unit, draws static terrain once, and redraws dynamic overlays when state changes. Target-only changes redraw a separate cursor and impact preview; the [32×32 browser profile](RENDER_PROFILE.md) records why this path was isolated. Movement search stores predecessor keys and reconstructs only the requested route; board highlights use reachable tile IDs. Enemy targeting skips moves whose damage preview is zero, including type immunity and absorption. `EnemyPlanner` checks decisions and attack-position path nodes in bounded batches, yielding to the browser between batches. The solo UI commits one action at a time and waits for movement or retained attack cues before continuing. The visual queue keeps no more than three waiting attacks, coalesces stale weather and repeated empty-target cues, and catches up with shorter animation timing when behind. Battle state retains only 24 recent cues; all are disposable and omitted from saves. Remaining route steps can be reused during the same enemy turn; changed targets or occupancy invalidate them. A saved battle may resume on an enemy turn and reconstruct the planner. Planning never rolls RNG, so combat and tie breaks remain reproducible from the saved battle state. Profile representative full matches before tuning larger maps or many units further. Keep combat outcomes in game state; animations only consume visual events and do not decide hits or damage.
