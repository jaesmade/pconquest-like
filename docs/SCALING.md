# Extending the early build

This guide describes the code that exists now and the contracts to keep stable as the game grows. The current run has a ten-column route with repeated encounter templates and simple enemy decisions.

Project development guidance lives in `AGENTS.md` and `docs/`. The former project-local `awesome-gamedev-agent-skills` bundle and its lock file were removed; extending the game does not depend on that skill pack.

The [scalability review](SCALABILITY_AUDIT.md) records the current growth limits and priorities for larger battles and content packs.

The [Pokefile content implementation plan](POKEFILE_CONTENT_IMPLEMENTATION_PLAN.md) covers the proposed import of the four reference CSVs, including temporary Movement 4, four equipped moves per Pokémon, effect rules, and rollout gates. The TypeScript catalogs below remain the current game data.

The [32×32 competitive 8v8 reassessment](SCALABILITY_TARGETS.md) sets the map ceiling alongside 20 total owned Pokémon per player and a 60 FPS rendering target. The current solo build supports up to 20 owned Pokémon and deploys six; competitive 8v8 and release performance remain future milestones.

The [ranked enemies and initial moveset rules](PLAN.md#proposed-enemy-ranks-and-automatic-latest-four-movesets) are implemented. `src/game/enemyRanks.ts` derives ranked rosters from explicit pools, level, seed, and node ID without changing combat RNG; it multiplies level-derived combat stats by 1×/2×/3× while leaving Movement alone. `src/game/movesets.ts` selects the latest four distinct eligible starting/level-up moves for fresh Pokémon. Manual level-up choices, TM teaching, owned equipped slots, evolution/form moves, and saved pending offers remain supported. All campaign maps support eight-enemy deployment through existing zone fallback. Saves write v28, preserve active v27 battles with hidden slots locked, and restart pre-v27 battles at preparation while retaining owned progression and moves.

Preparation and XP screens cache encounter derivation by route-node array, current node ID, encounter ID, and seed. Replace route-node arrays when changing their contents; party move choices and deployment updates do not change encounter identity. Startup validation caches map zones and origin/mobility reachability only within one `validateCatalog` call, so later mutations are rechecked. Save restoration calculates expected ranked stats once per unit while comparing every stat. See the [optimization review](SCALABILITY_AUDIT.md#2026-10-06-follow-up-ranked-encounter-optimization) for checks and measurement boundaries.

`src/content/data.ts` is a barrel for existing imports. New content can live in its focused file; battle scheduling stays in `src/game/engine.ts`, while effect-family rules live in `src/game/moveEffects.ts`.

The [ability overhaul](ABILITY_OVERHAUL_PLAN.md) adds distinct species `ability`/`hiddenAbility` defaults, saved per-Pokémon given/hidden choices and unlock state, and optional active `Unit.hiddenAbility`. All passive evaluators use both active slots; new combat callers must pass the unit to absorption and evasion helpers rather than only its given ID. Capsule/Patch use is explicit Bag metadata (`abilityUse`), excluded from equipment, with seeded pending Capsule choices stored on the run. New runs receive one of each for testing. Ordinary evolution preserves the owned profile; Mega Evolution temporarily supplies the form profile with the same hidden unlock.

`src/main.tsx` is only the entry point: it imports styles, validates content, loads the save, and mounts `App`. `src/app/App.tsx` coordinates the run and passes callbacks to screens in `src/ui/`. Shop and special choices render through `RouteStopScreen`; XP and level-up move choices through `IntermissionScreen`; held items, TM use, ordinary evolution, and evolution-item use through `RouteScreen`; completion through `ResultScreen`. `validateCatalog` checks evolution item source and target IDs. The route screen handles the compatible-Pokémon picker and shared evolution scene, while `src/game/engine.ts` validates and consumes the item, applies the form change, and updates learned moves and current HP. These screens do not own or serialize battle state. The split CSS files preserve the previous stylesheet order; `theme.css` applies the shared palette and `battle-menu.css` styles the glass action menu last. See the [UI overhaul plan](UI_OVERHAUL_PLAN.md) for color and typography conventions.

## Adding a Pokémon or move

1. Give the species and moves stable IDs. Existing IDs are stored in browser saves, so rename them only with a migration.
2. Add moves in `moves.ts` and the species' seven stats, types, ability, one or more distinct starting moves, level learnset, and optional `tmMoves` compatibility in `species.ts`. Stats are HP, Attack, Defense, Special Attack, Special Defense, Speed, and Movement, in that order. At creation, starting moves are ordered oldest to newest, followed by ascending level unlocks; the latest four distinct eligible moves are equipped (or fewer). Owned Pokémon retain their choices; a newly eligible level move can replace a slot only on the XP screen, and a TM can do so from the route Bag. Add `mobility: { fly: true }` or `{ swim: true }` for a form that needs it beyond the Flying/Water type defaults. Register any new ability in `abilities.ts` before assigning it to a species.
   The first six values are base combat stats. `statsAtLevel` derives HP, Attack, Defense, Special Attack, and Special Defense from level; Speed and Movement are copied directly from the species record and never change with level.
3. Add the species ID to `STARTERS`, `RECRUITS`, or an encounter only when it should appear there. A defined species can exist without joining either list.
4. Add battle art or let the renderer use the shared placeholder. New moves use role-based visual and sound placeholders automatically; set `visualId` and `soundId` to choose others. Add a named manifest entry keyed by the move ID when unique art or sound is ready.
5. Set an AP cost, tags, and an existing target area and effect in the move definition. `tags` is an array, so a move can have several. Supported tags are `contact`, `punch`, `bomb`, `projectile`, `pulse`, `sound`, `weather`, and `hazard`. Tag by what the move actually does: a future punching move would usually use `['punch', 'contact']`, while a thrown bomb could use `['bomb', 'projectile']`. The current starter moves have no punch or bomb move, so those tags are ready for future content without mislabeling Rock Throw or Tackle. Ability damage bonuses can use `requiredTag`; Tough Claws and Static now read the `contact` tag. The effect handlers cover status, displacement, tile effects, chain damage, stat stages, weather, and action advance or delay. One move use, including a Status move, consumes that Pokémon's Attack command for the turn; one Move command costs 1 AP within its Movement tile range. Special actions can also spend remaining AP. Existing item hooks cover cycle healing and threshold healing, Special Defense, Status move restrictions, Attack boosts, and Mega Evolution.

### Extending a move effect

Add a variant to `MoveEffect` in `src/game/types.ts`, then add its handler in `src/game/moveEffects.ts`. Each handler supplies `validate`, `resolve`, `preview`, and `score`. Startup catalog validation calls `validate`; combat calls `resolve`; the move hover card calls `preview`; and the solo enemy planner calls `score` to judge Status moves and break ties between damaging moves. The score hook reads battle state only and must not consume seeded RNG. The resolver may draw RNG through the battle's `random` function; any animation tiles it adds go on the provided visual cue and do not determine combat outcomes.

Execution order is fixed: cast effects run in their definition order, then direct targets are hit in battle-unit order; after each successful direct hit, its hit effects run in definition order. A chained hit checks that second defender's own accuracy, immunity, ability, and damage calculation, but does not repeat contact reactions or hit effects. Keep that distinction when adding a new effect. `src/game/engine.ts` owns AP spending, direct damage, and this phase order; no generic event bus is involved.

To add a held item, give it a stable name in `items.ts` and choose an existing effect shape. Consumables set `consume: true`; the battle unit keeps an Attack multiplier after X Attack is consumed. A Mega form is a complete species entry with its own stable ID, types, ability, stats, movement, moves, and art key. Put `form: { kind: 'mega', from: '<base-species-id>', stone: '<item-id>' }` on that form entry; do not nest Mega stats under the base species. `megaFormFor` indexes those relations for stone compatibility and battle transformation. Keep temporary forms out of starter and recruit lists. Item names and form species IDs are saved, so renaming either needs a migration.

Startup validation reports missing types, moves, evolutions, Mega Stones, encounter species, maps, objectives, spawn capacity, unusable deep-water spawns, and encounter-link cycles. It does not validate gameplay balance.

## Adding a map or encounter

Battle and deployment now use `src/battle/topDown.ts` for square 64×64 cells, without elevation displacement. The active top-down asset manifest supplies floors, cardinal ramps, ledge and shore borders, and cell-sized forest props. Unit source rows map logical south/west/east/north to `[0, 6, 2, 4]`. The old isometric renderer assets remain legacy material.

`createMap` accepts terrain rows (`.` plain, `~` deep water, `^` lava, `#` wall), matching elevation rows (`0`–`2`), and matching zone rows (`A` ally, `N` neutral, `E` enemy). All rows must have the same width, with a maximum of 32 rows and 32 columns. Every tile belongs to exactly one zone, and each side needs at least eight plain deployment tiles for future 8v8 battles. Default player spawns must be plain ground in the ally zone; enemy spawns must be in the enemy zone and off lava. Spawns must be unique. Every plain, unobstructed ally or enemy deployment tile and the capture tile must be reachable from the first ally spawn by a grounded Pokémon using the battle movement rules: deep water is impassable, elevation changes require correctly facing slopes, and walls and solid objects block movement. A neutral tile may be isolated if it is not a capture objective. Coordinates are zero based `[x, y]`.

During preparation, select a Pokémon and click a legal ally-zone cell; clicking an occupied cell swaps the two placements when both can use the destination. Water requires swimming or flight, and lava and walls are unavailable for deployment. The solo opponent chooses distinct legal enemy-zone cells using the battle's seeded RNG. `startBattle(run, enemyDeployment)` also accepts an explicit ordered enemy placement and rejects invalid, missing, or duplicate cells for a future competitive opponent. Neutral tiles cannot be used during deployment. Once battle starts, the zones do not restrict movement. Selected placements are part of the run save; older saves receive legal default positions.

Add the map to `MAPS`, then reference its ID from an entry in `ENCOUNTERS` or the normal campaign's `NORMAL_MAP_IDS` rotation. The encounter determines enemy species, objective (`defeat` or `defeat-and-capture`), and XP. An encounter using the capture objective needs a map capture tile. The engine and Phaser board use actual map dimensions for movement, attack areas, rendering, and weather cues. The campaign rotates five 16×16 normal forests by route column, retains a dedicated 16×16 elite lake, and uses an 8×8 ceremonial forest boss arena with an open stone dais and marked capture seal. All seven forests have grounded routes to heights 0–2 and clear ramps; their authored dirt trails also pass movement validation. The optional `surfaces` layer (`:` path, `,` moss, `=` stone, `*` seal) changes plain-tile art only. See the [battlefield asset guide](ISOMETRIC_ASSETS.md) for map identities, new object symbols, square top-down terrain borders, gallery, and `npm run verify:forest`.

### Proposed enemy levels above 100

Keep the player cap separate from the enemy level range. Use a player cap of 100 for `PartyMon`, XP awards, recruit levels, and player-unit save validation. Give encounter templates and enemy `Unit` snapshots a separate technical ceiling (provisionally 999) so opponents can exceed level 100 without allowing owned Pokémon to do so. Catalog validation and Battle Lab controls should validate ally and enemy levels against their respective limits.

Add a saved one-based `floorIndex` independent of the ten route columns and permanent unlock count. Migrate existing saves to floor 1. Keep floor 1's current node formula unchanged; later floors add a configurable floor offset after the normal/elite/boss level calculation. The route overview and balance baseline propose six levels per floor as a starting point, with the floor 15 boss at level 105; this value is for tuning, not an implemented rule. If floor routes keep the party climbing after the boss, preserve its level at no more than 100 and define how HP recovers between floors.

The current `statsAtLevel` formula already extrapolates HP and the four combat stats above 100; Speed and Movement remain fixed. Preserve that formula for enemies unless play data calls for a separate overlevel curve. Keep enemy move loadouts limited to authored learnset entries and four equipped moves. Save restoration must validate player battle units at 100 maximum and enemy units at the enemy ceiling; do not clamp over-level enemy battle snapshots to the player cap. The save format is currently v28, so adding `floorIndex` or changing enemy snapshot validation should ship with a migration (next available schema, currently v29) that defaults old runs to floor 1 and retains their party levels.

Encounter validation also checks each player species available through the starter/recruit evolution lines and each enemy species against every deployment cell it can legally use. Swimmers and flyers must be able to leave their chosen zone and reach the opposing land zone under their own mobility rules. An enemy water deployment must have adjacent ground that a grounded opponent can reach, so a water occupant can be confronted from shore. These are connectivity checks; they do not promise that a route through lava is survivable or that an AI will choose a good path.

The ten-column route records visited node IDs and the current node in the run. `run.encounter` tracks the current column for the UI. Authored encounters remain templates for map, enemy team, and objective; route battle and elite nodes adjust level, roster size, XP, and coins. The boss always uses the final authored map in column ten. Adding a node kind needs both a route resolver and saved-state migration.

## Saves and future rule families

Authored map fingerprints are cached by definition object reference, including the terrain-object/slope fingerprint. Treat catalog map objects as immutable after use; replace the definition with a new object when content changes. Battle tile effects continue to live in command-cloned maps and saved deltas, so they do not invalidate authored fingerprints. `npm run measure:save` verifies this separation and same-ID definition replacement while measuring synthetic save/clone costs.

The current format is v28 in the browser's IndexedDB database `pokemon-tactics-saves`. The `current` slot holds `{ schemaVersion, savedAt, run }` as JSON; the `backup` slot holds the previous complete snapshot. The run saves its route plan, visited nodes, coins, selected deployment coordinates, current node, and pending level-up move choices. Battle maps save an authored map ID and signature plus changed tiles; the signature includes deployment zones. Units retain combat state, next-action AV, scheduled Speed, per-turn Move and Attack flags, seeded RNG, owned hazard zones, and per-stat stage expiry, while transient animation events are omitted. Tile `hazardUntil` is derived from zones and omitted from v13 and later map changes. Loading restores the authored map, applies changed tiles, validates the battle, rebuilds hazard tiles, and falls back to the backup if the current slot is malformed. A changed authored map restarts that battle at preparation with a report message.

v7–v27 saves are accepted and subsequent writes use v28. Ability migration assigns locked hidden defaults to old parties and preserves active v27 battle ability IDs, queue, and RNG. v28 saves validate owned and Mega ability profiles and saved Capsule offers. Active pre-v27 battles restart at preparation for ranked enemies and scaled teams; owned progression, chosen/TM moves, pending offers, and route history are retained. New v28 battles preserve ranks, HP, stats, moves, both active ability IDs, RNG, and scheduled actions without applying bonuses again. The earlier v26 Speed-stage and v25 base-Speed migrations remain part of legacy handling. v21 and earlier active battles initialize the per-turn Move flag to false. Pre-v16 runs receive a generated ten-column route with center-lane history matching completed encounters; v16–v17 runs remap their route progress and current node onto the expanded graph. v20 and earlier active battles convert their action queue and old timer clock to AV while preserving the current actor, unless they are restarted by the v24 calibration or v25 base Speed migration. Current battles remain attached to their existing encounter template. The loader keeps party level and XP; v7–v10 saves also rescale current HP by the old and new maximum HP and return active battles to preparation because those units used the older combat-stat formula. A v11 battle resumes after its unit Movement values are restored from species data. Existing active Stealth Rock tiles in pre-v13 battles become temporary legacy zones with their original expiry because those saves did not record the caster; new casts cannot retroactively replace an unidentified old zone. Stages in pre-v14 active battles are capped at ±6 and receive the five-cycle timer. Pre-v17 saves keep their equipped moves, then gain missing species starting moves and fill the four-slot loadout; active battle units receive four moves without changing seeded combat state. v18 and earlier runs migrate with an empty pending move queue, retain their current equipped slots, and do not replay prior level-up offers. Loading accepts v7–v28 IndexedDB saves, v6 through v2 localStorage saves, and the older `pokemon-tactics-prototype-v1` shape. Legacy localStorage keys remain a fallback. React batches normal writes for 700 ms during battle and 150 ms outside battle. New Capsule offers instead save immediately, hide random names until the write succeeds, and retain the same hidden reservation for retry after failure (or allow cancelling that unrevealed failed use). Pending offers block route and upgrade engine calls. The app requests a final write when the page is hidden or closed; an abrupt browser termination can still lose the latest unsaved command. Storage failure appears in the top bar.

## Damage calculation

Damaging enemy target scans and attack-position search use `aimBoundsForTarget` to invert the move's unit/tile footprint before checking range and line of sight. Preserve the y-then-x candidate order and anchor/even-size behavior when extending areas. `npm run verify:targeting` checks ordered footprints, exhaustive hit equivalence, unchanged planner decisions/state/RNG, and a synthetic pursuit CPU benchmark; it does not measure browser FPS.

`src/game/damage.ts` is the single source for combat damage and UI ranges. It uses the attacking Pokémon's level, move power, the relevant Attack/Defense pair, standard stat stage ratios capped at −6 to +6, and integer base damage. Weather, a 1.5× critical hit, one of 16 equally likely random rolls from 85% to 100%, 1.5× same-type attack bonus, type effectiveness, and physical burn are applied in that order. Critical hits ignore negative offensive stages and positive defensive stages. The UI reports the possible normal and critical damage ranges; it does not consume battle RNG. The engine rolls critical chance (1 in 24) and damage variation when each target is hit.

Ability power bonuses are applied to base power, item Attack and Special Defense bonuses to the relevant stat, and snow/sandstorm defensive bonuses to Defense/Special Defense. Grid range, AP costs, terrain hazards, and secondary effects remain independent of direct move damage. New move-specific damage rules should be added as explicit calculator hooks rather than folded into a single final multiplier. Species stat growth in this fangame is still custom, so matching this damage pipeline does not imply complete main-series battle simulation.

When changing persisted fields, raise the schema version, keep a migration for existing versions, and preserve content IDs or map them explicitly. If a removed species, move, or encounter can occur in an old run, migrate it to an available replacement or reset that run deliberately; a type assertion alone cannot make old data valid.

Ability and item definitions and their supported effect settings live in `abilities.ts` and `items.ts`. Move definitions and areas live in `moves.ts`, with effect-family handlers in `moveEffects.ts`; pathfinding and line of sight live in `grid.ts`. `actionValue.ts` defines the 650,000-AV base action interval, 10,000-AV cycle, 65 Speed reference, duration conversion, and advance/delay operation. Temporary stages support Attack, Defense, Special Attack, Special Defense, and Speed at ±6; HP and Movement are excluded. Speed uses the shared stage ratio before ability/weather and paralysis, with fractional values retained. Speed-stage expiry is scheduled as an AV event, and its boost/drop appears as `Spd` in the stage badges. No current move applies a Speed stage yet. The engine selects the living unit with the lowest next-action time and reschedules waiting units when effective Speed changes; action effects can change a waiting unit's time or adjust the active unit's next scheduled action. Each turn adds 3 AP, and the per-turn flags limit a Pokémon to one Move command and one Attack command. Movement controls tile range; each Move costs 1 AP regardless of route length or terrain. Mobility capability and current state live in `mobility.ts` and on each battle unit. The Phaser board reads that state to draw a flight shadow or swim ripple.

The deployment SVG now keeps authored-map cell geometry and terrain elements stable across placement edits, indexes occupants by cell, and omits empty actor groups. It still renders a hit polygon for each tile; profile a future 32×32 preparation screen before introducing culling. The board creates a Phaser sprite and HP bar for each unit, draws static terrain once, and redraws dynamic overlays when state changes. Target-only changes redraw a separate cursor and impact preview; the [32×32 browser profile](RENDER_PROFILE.md) records why this path was isolated. Movement search stores predecessor keys and reconstructs only the requested route; board highlights use reachable tile IDs. Enemy targeting skips moves whose damage preview is zero, including type immunity and absorption. `EnemyPlanner` checks decisions and attack-position path nodes in bounded batches, yielding to the browser between batches. The solo UI commits one action at a time and waits for movement or retained attack cues before continuing. The visual queue keeps no more than three waiting attacks, coalesces stale weather and repeated empty-target cues, and catches up with shorter animation timing when behind. Battle state retains only 24 recent cues; all are disposable and omitted from saves. The enemy planner can move once per turn, then continues looking for an attack; it cannot reuse remaining route steps for a second Move command. A saved battle may resume on an enemy turn and reconstruct the planner. Planning never rolls RNG, so combat and tie breaks remain reproducible from the saved battle state. Profile representative full matches before tuning larger maps or many units further. Keep combat outcomes in game state; animations only consume visual events and do not decide hits or damage.
