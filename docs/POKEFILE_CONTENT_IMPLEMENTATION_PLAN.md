# Pokefile content implementation plan

**Status:** Plan only, 2026-09-30. The four CSVs are reference data; the game currently uses hand-authored TypeScript catalogs. This document defines the rollout and its acceptance gates. It does not mark any CSV row as implemented.

Current missing fields and row-specific decisions are tracked in [Content Information Gaps.csv](../pokefiles/Content%20Information%20Gaps.csv). Rows with a shared filter capture repeated gaps; source row numbers identify entry-specific blockers. Fill the requested information and record the decision in its Resolution column before implementing blocked content. The [Gen 7-9 Move Reference](../pokefiles/output/Pokemon%20Moves%20Gen7-9%20Reference.csv) covers 919 moves in the combined Gen 7-9 main-series scope. It preserves existing Moves.csv powers, descriptions, implementation notes, targets, and delivery while adding current power, accuracy and effect chances, damage class, move traits, flags, and timing metadata. The description version note flags moves with separate Gen 7 or Gen 8 text; five blank source descriptions use concise summaries from their implementation notes.

## Consolidated Pokefile reference export

The checked [Pokemon reference CSV](../pokefiles/for%20checking/Pokemon%20Reference.csv) has one row for each of the 1,351 dex/form rows in `Pokemon Stats.csv`. It is reference data only; it does not register any row in the runtime catalogs or mark the staged content rollout as implemented.

- National Dex number, name, form key, six base stats, and ordered types come directly from `Pokemon Stats.csv`.
- Evolution paths and conditions, possible ability slots, form-specific move records, and region labels are joined from the pinned [PokeAPI CSV data](https://github.com/PokeAPI/pokeapi/tree/89289e314ae20a34e8159a34a5fe646e656d6149/data/v2/csv) snapshot (`89289e314ae20a34e8159a34a5fe646e656d6149`). The six base stats and types were not replaced by API values.
- `Learnset Moves` is the union of moves recorded across PokeAPI version groups. `Learnset Rules` combines each move's methods and all recorded levels across those groups; it does not preserve a separate level for each game. Transformed forms with no separate PokeAPI learnset inherit their default species form's learnset and are marked in the status/note columns.
- `Available TMs` uses the project's 229 entries in `TM.csv`, matched by move name to PokeAPI machine compatibility. For each form, the export selects Scarlet/Violet records first, then Sword/Shield, then the latest earlier version group that records machine/TM compatibility and has a move record for that form. Games without TM compatibility data are skipped. Mega, Gigantamax, and battle-only forms with no eligible form-specific record inherit the default form's selected compatibility. The CSV records the source version group, reports forms with no eligible record explicitly, and flags selected source groups with no match in the project's TM list. TM numbers remain the project's `TM.csv` numbers; they are not remapped to each source game's numbering.
- `Origin Region` is the species' main region based on its introduction generation. `Form Region` identifies Alola, Galar, Hisui, or Paldea regional forms separately.
- `exp gain` records the species' experience growth curve for every form, using the pinned PokeAPI `pokemon_species.csv` and `growth_rates.csv` tables. Labels include Slow, Medium Fast, Fast, Medium Slow, Slow Then Very Fast, and Fast Then Very Slow. The export is reference-only; runtime XP still uses one shared threshold. See the [experience growth plan](EXP_GROWTH_PLAN.md) for the proposed species-aware runtime mapping, save migration, and reward rebalance.
- The output includes evolution target, level, method, and condition columns; ability options preserve slot order and the hidden flag. Nine Mega forms have no ability records in the pinned PokeAPI snapshot, so those cells are empty and flagged instead of guessed.

Regenerate the checked copy with [the reference CSV generator](../scripts/generate_pokemon_reference_csv.py), passing `--output "pokefiles/for checking/Pokemon Reference.csv"`. It fetches the pinned PokeAPI tables when no local source folder is passed.

## Item reference export

The generated [Pokemon Items Reference CSV](../pokefiles/output/Pokemon%20Items%20Reference.csv) covers every row in [Items.csv](../pokefiles/Items.csv) and appends the current runtime-only item definitions. It is descriptive reference data; it does not register items or change game behavior.

- Each source row keeps its category, source row number, description, and proposed game implementation. Repeated names remain separate and retain their row context.
- The export marks whether each item currently has a definition in `src/content/items.ts` and includes that definition's runtime description. The current catalog has eight definitions: five overlap the source list, while `None`, `TM Swift`, and `TM Thunderbolt` are runtime-only.
- All 459 source rows are present. Twenty-eight source descriptions are blank and explicitly flagged; the generator does not invent missing item effects.
- Regenerate it with [the item reference CSV generator](../scripts/generate_pokemon_items_reference_csv.py). The scope is the project Pokefile plus its runtime-only entries, not every item ever released across all Pokémon games.

## Decisions for the testing rollout

1. Use the six original base stats and the ordered one or two types in [Pokemon Stats.csv](../pokefiles/Pokemon%20Stats.csv). Append **Movement = 4** as the seventh stat for every PokÃ©mon and form during testing. Movement is tile range, not Speed or AP gain. Keep the source base stats unchanged.
2. Give every battle-ready PokÃ©mon **four distinct equipped moves**. The four CSVs do not provide species move sets, learnsets, or TM compatibility, so author those links in reviewed supplemental content. Keep the current limit of one Attack command per turn and 3 AP gained per turn; four slots are four choices, not four attacks.
3. Preserve every `Power` value in [Moves.csv](../pokefiles/Moves.csv). Its numeric value is the target for a migrated ordinary damaging move. Blank, zero, inherited, fixed-damage, and variable-power entries require an explicit rule before activation. The CSV's AP, range, target, delivery, and implementation prose are proposed game mappings that need validation against the actual rule engine.
4. Preserve saved species, move, ability, and item IDs through explicit aliases or a save migration. An existing playable entry retains its current behavior until its CSV mapping and balance change are reviewed and released together. Record intentional runtime exceptions beside the mapping; never silently replace an existing move's power, area, AP cost, or availability.

## Content pipeline

1. Parse each CSV at build time into a **reference manifest** that retains its source row, original text and numbers, and a stable source key. Generate a coverage report with one outcome per row: `playable`, `needs-rule`, `needs-link`, `source-unavailable`, or `nonbattle`. A row may have more than one reason. In Moves.csv, `CURRENT RULES` often means an existing handler can be reused; it does not prove the named move is in `MOVES`. Check runtime membership separately.
2. Maintain reviewed crosswalks from source keys to stable runtime IDs and from source descriptions to typed rule definitions. Keep metadata for every row, but publish into the playable catalog only after its rule, references, and availability validate. Reject duplicate or ambiguous name-only lookups. `As One` appears twice with identical text, `Fishing Rod` appears twice with different descriptions, and 18 Z-Move names each appear twice; resolve them with source and variant context. Form keys such as `0386 (normal)` also need explicit IDs. Retain the game's `None` sentinel and TM items even though the CSV omits them.
3. Extend `validateCatalog` and the import report to check unique IDs, source coverage, type names, positive stats, legal AP and target rules, item use kinds, effect parameters, form/evolution links, ability assignments, and distinct valid starting/level-up moves. A missing rule or link blocks playable registration with a specific reason. Do not register description-only abilities or nonbattle items as inert battle content.

### PokÃ©mon and forms

Split `Type` on ` / ` into an ordered one- or two-type list and check against the 18-type chart. Keep all six CSV stat values exact. `statsAtLevel` derives HP, Attack, Defense, Special Attack, and Special Defense from level, while preserving source Speed and copying Movement unchanged. Provide an explicit CSV row-to-species ID map, including the 363 suffixed form keys. Classify ordinary evolutions, alternate forms, Mega forms, and Gigantamax entries separately; a listed form is not automatically a recruit.

The `Evolves:` field names targets but supplies neither levels nor conditions. It includes branched targets and names that only match specific forms. Author target IDs and conditions in a separate evolution mapping, with validation for unresolved branches. Review the existing Charmander-to-Mega-Charizard-X shortcut against the CSV's Charizard Mega X row and stone compatibility before publishing that form from the import. Assign species abilities, four starting moves, later learnsets, and TM compatibility from curated mappings; type similarity alone must not invent a loadout.

### Moves

Classify all 919 rows before runtime import. At present 109 are marked `Unavailable` with AP 0, 37 inherit their base move, and some remaining damaging rows have blank or zero power and need fixed, variable, or other special formulas. Duplicate Z-Move display names need distinct IDs tied to their base-move context. The CSV's `Delivery` values include Area, Field, Self, and Status, while the current damaging `Move` contract accepts melee or ranged delivery; map target selection, area, and damage delivery as separate properties. Review accuracy/chance text and the generated implementation notes row by row rather than compiling them as instructions. In particular, 98 generated notes propose a spurious `0% accuracy check`; none should become a battle rule without correction.

The current game and CSV differ for some authored moves: for example, Thunderbolt is power 75, 4 AP, and area-targeted in code, while the CSV proposes power 90, 3 AP, and a unit target; Bubble is playable in code but marked unavailable in the CSV. The move crosswalk must record the planned runtime change, any intentional override, and the save impact before each migration batch. If Bubble becomes unavailable, replace it in Squirtle, Wartortle, and Lapras's starting sets in that same batch so each still has four legal moves. Keep CSV power untouched throughout.

### Abilities and items

Use typed effect families with explicit trigger phases, target scope, magnitude, chance, duration, consumption, and suppression rules. Define deterministic ordering where a move, ability, and held item react to the same event. Review prose that conflicts with the described effect, including `Stance Change` and `Toxic Chain`, before coding it. Keep ability metadata browsable without assigning an unimplemented effect to a playable species.

Item category alone is not a use rule. The current `itemCanEquip` accepts almost any defined non-TM item, so bulk-registering the CSV would make medicines and key items equippable without a useful effect. Add an explicit item use kind and availability gate first. Resolve 28 blank item descriptions, the two different `Fishing Rod` rows, prices, route acquisition, compatibility, and consumption in reviewed supplemental data. Preserve the existing `None`, `TM Swift`, and `TM Thunderbolt` IDs; the CSV does not contain these individual TM items. Abilities and items that require switching, fleeing, ally pairing, or another absent command remain unavailable until those actions exist. The [item reference export](../pokefiles/output/Pokemon%20Items%20Reference.csv) exposes the current source descriptions and implementation proposals, preserves repeated names by row, flags those 28 missing descriptions, and distinguishes the eight implemented runtime definitions from reference-only items.

## Save and balance gates

- Current saves use schema v27 and store species, learned/equipped moves, items, battle units, stats, and action timing. The v27 migration restarts active older battles at preparation for ranked enemies while retaining owned progression, chosen moves, and pending level-up offers. New v27 snapshots validate/persist ranks and intrinsic stats. The earlier v26 migration added inactive Speed stages. The v25 base Speed change restarts active pre-v25 battles at preparation with a clear report because their saved battle units contain level-derived Speed; party and run progression remain. Future source-content batches that change other stats or IDs still need explicit migrations, aliases, and a defined HP reconciliation policy.
- Species Speed now uses its original CSV base value at every level. The current 11 runtime forms average 63.27, near the AV and Trick Room reference of 65; a base Speed of 20 therefore remains 20 as a Pokémon levels. Keep future source Speed values exact and review roster pacing, weather/status durations, enemy actions, Trick Room interactions, and the 3-AP turn economy as the catalog expands.
- Movement 4 changes route reach, hazards, and attack positioning on existing maps. Review player and enemy pathfinding and deployment with the four-tile test value. Keep the four-move loadout visible in the existing Attack menu and honor the one-Attack-per-turn limit.

## Completion checks for each release batch

Record the source-row coverage and unresolved reasons; compare imported stats, types, and ordinary move power with the CSV without editing the source files. Check representative single and dual types, normal and temporary forms, four-tile movement, four distinct equipped moves, AP legality, each new move/ability/item trigger, seeded chance rolls, preview versus actual outcome, AI use, and save round trips. Run the catalog validator, focused Battle Lab cases, a campaign playthrough, and large-catalog UI/performance checks when implementation begins. A batch is playable only when its dependencies and checks pass; remaining rows stay visible in the coverage report as planned content. The full rollout is complete only when every eligible row is playable or intentionally classified as nonbattle or source-unavailable, with no unresolved `needs-rule` or `needs-link` rows.
