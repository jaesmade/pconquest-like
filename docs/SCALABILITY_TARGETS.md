# Scalability reassessment: 32×32, competitive 8v8

Assessment date: 2026-09-28. Target scope is a square map up to 32×32 tiles, two human players with up to eight deployed Pokémon each, up to 20 total owned Pokémon per player in a run, and at least 60 rendered frames per second. The current build is an 8×8, local, single-player prototype with up to 20 owned Pokémon and up to six deployed. This document records the work needed to meet the new limits; it does not claim that the current build meets them.

## Evidence and frame budget

At 60 FPS, each frame has 16.67 ms for browser scripting, rendering, and compositing. `node scripts/measure-save.mjs` measures only Node-side state operations on synthetic maps. The 32×32, 16-unit, 20-owned scenario produces a roughly 12 KB compact save, with command cloning and JSON serialization well below 1 ms on the local machine. Those costs are small relative to the frame budget. The benchmark does not measure IndexedDB latency or network traffic. A separate [32×32 browser rendering profile](RENDER_PROFILE.md) now measures the minified Phaser board at 8v8 and records frame intervals, draw calls, JavaScript heap, and long tasks. Its synthetic scene stayed near 60 Hz on the reference browser; GPU time and slower devices remain unmeasured.

A far pursuit on an open 32×32 map required 14 batches of 32 search nodes, with 2.65 ms total search CPU. At one batch per rendered frame, that spans about 0.23 seconds at 60 FPS before the unit acts. This is a solo/bot responsiveness cost to watch; competitive human matches do not run this planner. The measurements vary with hardware and map layout.

The current `Board` sizes its Phaser canvas to the board container. At 32×32, the top-down world is 2176×2176 pixels; its full-map terrain render texture represents about 18.1 MiB of RGBA pixels before renderer copies. The board draws 1,024 terrain cells into that texture at scene creation. Camera pan/zoom and screen-to-world pointer conversion are implemented. Target cursor movement redraws a small preview; attack-range line-of-sight results are cached across compatible battle changes. Full dynamic scans remain for battle and mode changes. The [current browser profile](RENDER_PROFILE.md) does not justify visible-cell culling or a chunked terrain rewrite yet.

## Architecture decisions for the next build

1. Keep the tactical rules independent of Phaser, React, storage, and sockets. A command should be plain data such as `{ matchId, commandId, expectedRevision, actorUnitId, action }`; the reducer returns the next authoritative state and ordered rule events. The server is the only writer in competitive matches.
2. Send commands and compact state deltas rather than an entire map after every action. Send the authored map ID/content version once, a complete snapshot on join/reconnect, then revisioned unit and tile changes. Reject or resync when a client misses a revision.
3. Keep 60 FPS as a rendering target separate from network command latency. Turn resolution can wait for the server without blocking pan, hover, menus, or cosmetic playback. Set a reference browser, device, resolution, and device-pixel ratio before claiming compliance.
4. Preserve local solo mode as a separate match adapter that calls the same reducer. A bot submits commands through the same validation boundary; it cannot mutate authoritative state directly.

## Release gate for these limits

Profile a production build on a declared reference device with a 32×32 map, 16 battle units, 20 owned Pokémon per participant, hazards, weather, area attacks, board navigation, and the maximum expected animation load. Record p50/p95/p99 frame time, main-thread long tasks, GPU time, canvas/texture memory, command latency, snapshot/delta bytes, reconnect time, and server CPU/memory per match. The Node save benchmark and synthetic browser rendering profiles cover only parts of that gate; they do not establish the 60 FPS target or multiplayer capacity.
